<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Developer commit → GitHub Pages build runner | Code/config crosses from local repo to the build environment; misconfig propagates publicly |
| GitHub Pages build → visitor browser | Static HTML/meta tags served unmodified to anonymous internet users |
| Repo files → public git history | Anything committed becomes permanent public record |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Information Disclosure | `_config.yml` author/social fields | mitigate | D-04: strip `social_links:` and `author.email:` entirely so jekyll-seo-tag does NOT emit stub `twitter.com/your_twitter_handle` schema.org sameAs entries (RESEARCH.md Pitfall 5); acceptance criteria assert these fields are absent |
| T-01-02 | Tampering | `Gemfile` version pin | mitigate | Pin `gem "github-pages", "~> 232"` (D-11) so build is locked to GitHub Pages-vetted Jekyll 3.10.0; pessimistic constraint allows patches but blocks Jekyll 4.x which is incompatible with GitHub Pages safe mode |
| T-01-03 | Repudiation | `Gemfile.lock` accidentally committed | mitigate | Add `Gemfile.lock` to `.gitignore` (Task 2) so local lockfile cannot drift live build state; GitHub Pages ignores Gemfile.lock anyway, but ignoring it locally prevents noisy diffs and contributor confusion |
| T-01-04 | Information Disclosure | Stale URL placeholder leaking to canonical tags / sitemap | mitigate | Replace `https://kanha_studyjournal.github.io` placeholder with real `https://songeamkanha.github.io` (D-01) before any build runs — otherwise jekyll-sitemap emits broken canonical URLs to search engines |
| T-01-05 | Denial of Service | Build warning fatigue masking real issues | mitigate | Remove `paginate:` + `paginate_path:` (no backing gem) so build log is clean; future real warnings remain visible (RESEARCH.md Pitfall 1) |
| T-01-06 | Spoofing | Third-party XSS via Markdown content | accept | Phase 1 has no user-supplied markdown — only one author-written test post in Plan 02. kramdown safe mode + GitHub Pages `safe: true` mitigates inherent XSS for any future markdown |
</threat_model>
